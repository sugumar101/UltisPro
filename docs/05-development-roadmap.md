# UltisPro — Development Roadmap

Every module is built through the same 19-step process you specified (Requirements → DB Schema → ER Diagram → Folder Structure → Models → DTOs → Validation → Repository → Services → APIs → Auth wiring → Frontend Pages → Components → State Management → Forms → API Integration → Unit Tests → Integration Tests → Documentation). Nothing skips ahead; each module gets your explicit approval before the next one starts, as instructed.

This roadmap sequences *which* module goes through that process, and in what order, based on dependency chains from 04-module-breakdown.md.

## Phase 0 — Foundation (M0)
Monorepo scaffold, Docker Compose (Postgres, Redis), Nginx config, GitHub Actions skeleton (lint/typecheck/test), base Express app with error middleware/logger/health checks, base Next.js app shell with the design system tokens wired into Tailwind config, shared Zod/type package, DI container pattern.
**Exit criteria:** `docker compose up` boots API + web + Postgres + Redis; CI runs green on an empty test suite; a hello-world authenticated round trip works end-to-end.

## Phase 1 — Identity & Tenancy (M1 → M2 → M3)
Auth (login/refresh/logout/password reset) → Organizations/Stores/Branches → Users/Roles/Permissions.
**Why first:** every other module's tables carry `organization_id` and every endpoint requires RBAC — nothing else can be meaningfully built or tested without this.
**Exit criteria:** an org admin can sign up, create a store + branch, invite a cashier with a scoped role, and the cashier can log in and see only what their role permits.

## Phase 2 — Catalog & Inventory Core (M4 → M5) — ✅ Complete
Products/Categories/Brands/Units/Taxes → branch_stock/stock_ledger/adjustments/transfers/low-stock alerts.
**Why next:** POS, purchasing, and reports all read from the catalog and stock ledger; this is the data backbone.
**Exit criteria:** products (simple and variant) can be created with correct GST/HSN, stock can be manually adjusted, and the stock ledger reconciliation invariant (`SUM(quantity_delta) == quantity_on_hand`) holds under test.
**Delivered:** migrations 0004 (catalog) + 0005 (inventory); Categories/Brands/Units/Taxes CRUD modules; Products module with variant builder and per-org reference validation; `applyStockMovement()` as the single choke point for stock writes (adjustments + transfers), enforcing the reconciliation invariant via row-locked transactions; frontend Products list/detail/create pages, Inventory stock + adjustment page, and a Catalog Setup settings tab. Covered by `apps/api/test/products-inventory.test.ts`, including a test that a would-go-negative adjustment is rejected with no ledger write, and a two-branch transfer dispatch/receive round trip.

## Phase 3 — Procurement (M6) — ✅ Complete
Suppliers → Purchase Orders → Receiving (writes stock_ledger) → Purchase Returns → Supplier Payments.
**Exit criteria:** a PO can be raised, partially received, and the received quantity correctly increments stock and decrements PO outstanding; supplier outstanding balance is accurate.
**Delivered:** migration 0006; Suppliers CRUD + payment recording; Purchase Orders with draft → approved → partially_received/received → cancelled lifecycle, row-locked receiving (so concurrent/partial receipts converge correctly), and Purchase Returns that reverse stock and supplier balance. Frontend: Suppliers list/detail with payment history, PO create/detail/approve/receive, one-click "return all received stock." Covered by `apps/api/test/purchasing.test.ts`: total computation, the full approve→partial-receive→over-receive-rejected→full-receive flow (asserting stock and supplier balance at each step), purchase returns (including over-return rejection), supplier payments, and PO cancellation rules. Two MVP simplifications documented in `docs/03-database-design.md` §13: PO numbers are a random code, not a gapless sequence; receiving always lands in unbatched stock.

## Phase 4 — Customers (M7) — ✅ Complete (MVP scope)
Customers/Addresses → credit limit & outstanding → (P1: loyalty, vouchers, store credit).
**Exit criteria:** a customer can be created inline from POS, credit-limit checks work, purchase history query returns correct invoices.
**Delivered:** migration 0007; Customers + Addresses CRUD, row-locked `charge`/`payments` endpoints enforcing the credit limit, and a walk-in customer auto-seeded at org signup. Covered by `apps/api/test/customers.test.ts`: walk-in seeding and delete-protection, duplicate-phone rejection, charge-within-limit/at-limit/over-limit (including the zero-credit-limit default), payments reducing balance, and address default-swapping. Two exit-criteria items are necessarily partial until Phase 5 ships: "created inline from POS" has no POS yet (the quick-add API exists and is ready for POS to call); "purchase history returns correct invoices" can't be tested until `sales_invoices` exists — `/customers/:id/history` is deferred to Phase 5, documented in `docs/04-module-breakdown.md` M7.

## Phase 5 — POS & Sales (M8 → M9) — ✅ Complete (MVP scope; printing deferred)
This is the flagship phase: barcode/search add-to-cart, hold/resume, discounts, split payment, checkout → invoice generation with gapless sequential numbering → PDF/print → sales returns/credit notes.
**Why after Phase 2–4, not before:** POS is the consumer of catalog, stock, and customer data — building it first would mean mocking all three; building it now means it runs against real data end-to-end from day one.
**Exit criteria:** a full sale can be rung up with a barcode scanner and keyboard shortcuts only, split across two payment modes, printed to a thermal printer, and reversed via a return that correctly restores stock.
**Delivered:** migration 0008; POS screen (search/scan-to-add, editable cart, hold/resume, split payment); `/sales` checkout — one transaction handling gapless invoice numbering, per-line stock deduction, payment recording, and on-account shortfall charged to the customer (credit-limit enforced, rejected outright for the walk-in customer); sales returns restoring stock and crediting the customer account, with per-line cumulative-return tracking driving `partially_returned`/`returned` status. Covered by `apps/api/test/sales.test.ts`: sequential invoice numbering across back-to-back sales, stock decrement + total computation, negative-stock rejection, walk-in credit rejection, split payment with in-limit shortfall charge, over-limit shortfall rejection, full return (stock restored, status flips to `returned`, over-return rejected), POS search, and hold/resume. **Not delivered at the time:** invoice PDF generation and thermal receipt printing — deferred to **Phase 10 below, which has since closed this gap**; the "printed to a thermal printer" exit criterion is now met. Barcode *scanning* works via keyboard-wedge input into the POS search box.

## Phase 6 — Dashboard & Reports (M12 → M11) — ✅ Complete (MVP scope)
Dashboard KPIs/charts first (simpler aggregates, immediate visible payoff), then the full report suite with CSV/Excel/PDF export.
**Exit criteria:** dashboard reflects live data from Phases 2–5; GST summary report matches manually-calculated tax totals for a test dataset.
**Delivered:** no new tables — this phase is pure read-side aggregation over Phases 2–5's data. Dashboard (`/dashboard/summary`, `/charts`, `/recent-activity`) and Reports (`/reports/sales`, `/inventory`, `/gst`, `/cash-flow`, each with CSV export) plus matching frontend (KPI cards + trend chart on Dashboard; a tabbed report picker with date-range filtering on Reports). Covered by `apps/api/test/dashboard-reports.test.ts`, which builds one known taxed sale and one known taxed purchase receipt and asserts the aggregates hand-computed from that data exactly — including the GST report's CGST/SGST split and its output-minus-input net (which comes out negative in the test, correctly modeling a refund position). Excel/PDF export and the P1 report types (purchases/customers/suppliers as standalone reports) are not built.

## Phase 7 — Expenses, Notifications & Audit Surface (M10 → M13) — ✅ Complete
Expense tracking; notification center UI (the audit *logging engine* itself is wired in from Phase 1 onward as a cross-cutting concern, per 04-module-breakdown.md).
**Exit criteria:** expenses feed into P&L; low-stock/expiry events surface as in-app notifications; audit log viewer shows an accurate before/after trail for a sample set of mutations.
**Delivered:** migration 0009 (`expense_categories`, `expenses`, `notifications`); `/expenses` + `/expense-categories` CRUD with a filterable list page; on-demand, idempotent notification generation for low-stock/expiring-batch conditions surfaced via a header bell (60s poll, unread badge, mark-read); `/audit-logs` viewer filterable by entity table/id/actor, gated by `AUDIT_VIEW`. Covered by `apps/api/test/expenses-notifications-audit.test.ts`: expense category + expense creation, cross-org expense rejection, low-stock notification generation with duplicate-prevention on repeat polls, mark-read, and an audit-log before/after trail check on a product create+update pair. **Not delivered:** a background worker pushing notifications proactively (generation is lazy, on read) and per-user read-state for broadcast notifications — both documented as P1 in `docs/03-database-design.md` §17.

## Phase 8 — Hardening & Launch Readiness — ⚠️ Partially complete (sandbox-limited)
Security review (rate limiting, RLS policy audit, dependency scan), load testing the POS checkout path, accessibility pass on admin screens, offline-indicator UX, full export coverage, production AWS deployment (ECS/RDS/ElastiCache/S3/CloudFront), GitHub Actions promoted to gated staging→prod pipeline.
**Exit criteria:** the system is demoable end-to-end as a sellable product for a pilot retail customer.
**Delivered:** rate limiting on the four credential-facing auth endpoints (register-organization, login, password/forgot, password/reset), unit-tested in `apps/api/test/rate-limit.test.ts`; a documented RLS audit finding — tenant isolation today is application-layer (`organization_id` filtering, manually enforced per repository method) rather than native Postgres RLS, with the concrete steps to close that gap written up in `docs/03-database-design.md` §18; a manual dependency review of all three `package.json` files plus a new `.github/dependabot.yml` for ongoing patch coverage. Every phase 0–7 module, its API + frontend + Vitest suite, and its documentation is now marked complete across `docs/03-database-design.md`, `docs/04-module-breakdown.md`, this roadmap, and `README.md`.
**Not delivered (requires real infrastructure/tooling this sandboxed, shell-less build doesn't have):** load testing the POS checkout path, an automated accessibility audit, offline-indicator UX, Excel/PDF report export, production AWS deployment, and promoting the existing `.github/workflows/ci.yml` (lint/typecheck/migrate/test/build against service containers, already in place) to a gated staging→prod pipeline. These are the concrete, named remainder before a pilot customer goes live — see `docs/03-database-design.md` §18 for the full reasoning per item. **Standing environment action items, not yet performed because this session never had shell access:** delete `apps/web/next.config.ts` (superseded), delete `apps/api/src/modules/auth-scaffold/` (Phase 0 throwaway code, already unwired from `app.ts`), run `npm install` (no lockfile exists yet — dependency versions are ranges, not pinned), then `npm run migrate` to apply migrations 0001–0009 against a real database.

## Phase 9 — Clothing Product Taxonomy (post-launch enhancement) — ✅ Complete
Not part of the original 8-phase plan — added afterward in direct response to a real gap surfaced once the app was actually running: the generic Products flow had no way to model a clothing retailer's type→category taxonomy, gender, multi-size variant creation, or an auto-generated product code.
**Exit criteria:** an admin can define Product Types (e.g. T-Shirts, Pants) with their own size lists and nested Product Categories entirely through the UI (no hardcoded taxonomy), then create a clothing product picking a type/category/gender, checking multiple sizes with a quantity each, and have it land as one product with one variant per size, a 5-digit product code, and opening stock already posted to a branch.
**Delivered:** migration `0010_product_taxonomy.sql` (`product_types` with `size_options`, `product_categories` nested under a type, four new nullable columns on `products`); new `product-types` backend module; `POST /products/clothing` on the existing Products module, reusing the Inventory module's exact stock-adjustment/`applyStockMovement` path for opening stock; two new Settings > Catalog panels for managing types/categories; a new `/products/new-clothing` screen. Covered by `apps/api/test/product-taxonomy.test.ts` — type/category creation, cross-org rejection, multi-size product creation with correct SKUs/product code/opening stock verified against `/inventory/stock`, zero-quantity sizes not posting stock, duplicate-size rejection, and category/type mismatch rejection. See `docs/03-database-design.md` §19 for the full design writeup, including why this used new tables instead of the existing `categories` hierarchy.
**Not delivered:** image upload for clothing products (explicitly scoped out — no storage backend configured in this environment).

## Phase 10 — Receipt & Tax-Invoice Printing (post-launch enhancement) — ✅ Complete
Closes the largest remaining MVP gap: POS-08 (thermal receipt printing) and SAL-02 (invoice PDF) were both marked MVP-mandatory in `docs/01-functional-requirements.md` but shipped as stubs — a completed sale produced no customer-facing document at all, which is the difference between a demo and something a shop can run a counter on.
**Exit criteria:** a cashier completes a sale and a receipt prints without leaving the POS screen; any past invoice can be reprinted as either an 80mm receipt or a full A4 GST tax invoice, with a rate-wise tax summary that reconciles exactly to the invoice's stored totals.
**Delivered:** no new tables — this is pure read-side rendering over Phase 5's data. `GET /sales/:id/receipt` assembles the whole document server-side (joined line items with product name/SKU/HSN, letterhead, customer, cashier, rate-wise CGST/SGST/IGST summary, amount in words via the new `shared/amount-in-words.ts` using Indian lakh/crore grouping); `/sales/:id/print` renders it as either an 80mm thermal receipt or an A4 tax invoice, printed through the browser's own print pipeline; POS auto-prints after checkout (toggleable) and keeps the last sale pinned for reprint; the invoice detail page gained Print/A4 actions and now shows real product names instead of raw variant UUIDs. Covered by `apps/api/test/sales-receipt.test.ts` (joined-data correctness, GST summary reconciling to `tax_total`, amount-in-words, cross-org 404, auth gate) and `apps/api/test/amount-in-words.test.ts` (Indian grouping boundaries, paise, negatives).
**Not delivered:** S3 archival of generated PDFs (SAL-02's second half — no storage backend configured in this environment), and cash-drawer kick / paper auto-cut, which need real ESC/POS control bytes through a local print agent rather than the browser print pipeline. See `docs/03-database-design.md` §20 for the full reasoning on the browser-print-vs-server-PDF choice.

## Phase 11 — Product Entry: inline masters & auto barcodes (post-launch enhancement) — ✅ Complete
Two friction points found by actually adding products on a fresh organization: the Category and Brand dropdowns were empty (a new org has no masters, and nothing on the form could create one), and every variant needed a barcode typed by hand — unworkable for a clothing shop whose garments arrive with no scannable code.
**Exit criteria:** a user can add a product on a brand-new organization without visiting Settings first, typing a category and brand that don't exist yet; and every saved variant comes out with a scannable barcode without anyone entering one.
**Delivered:** no schema changes. `categoryName`/`brandName` accepted on `POST /products` and `brandName` on `POST /products/clothing`, resolved find-or-create (case-insensitive, resolved before the product transaction so a retry doesn't duplicate the master); both forms switched from `<select>` to a text input backed by a `<datalist>` of existing values. `shared/barcode.ts` generates in-store EAN-13s using the GS1 `20`–`29` restricted-circulation prefix, applied to any variant saved without a barcode — one per clothing size, surfaced on the post-save screen for label printing. Covered by `apps/api/test/products-autofill.test.ts` (inline creation, case-insensitive reuse, no-duplicate assertion, auto/manual barcode, per-size barcodes) and `apps/api/test/barcode.test.ts` (checksum against known-good published EAN-13s, prefix, uniqueness).

## Phase 12 — HSN defaults & full master-data editing (post-launch enhancement) — ✅ Complete
Products could be created but never corrected: nothing in the UI exposed edit or delete for products, variants, or any catalog master, so a typo meant living with it. Separately, HSN had to be typed per product from memory.
**Exit criteria:** every product, variant, category, brand, unit, tax rate, product type and product category can be renamed and removed from the UI; and a product created without an HSN code gets a correct standard one wherever the wording makes it unambiguous.
**Delivered:** migration `0011_product_type_hsn.sql` (`product_types.default_hsn_code`); `shared/hsn.ts` mapping product wording onto real standard HSN codes with an inheritance chain (product type's confirmed code → suggestion from type + product name → null); a shared `EditableListRow` component wired into all six master lists in Settings > Catalog; an editable product detail page with per-variant edit, add and delete; Edit/Delete actions on the products list. The one genuinely missing backend piece was `DELETE /products/:id/variants/:variantId`, which was added with a guard refusing to remove a product's last variant. Covered by `apps/api/test/hsn.test.ts` (rule ordering, case-insensitivity, null-on-no-match) and `apps/api/test/products-crud.test.ts` (HSN suggestion/inheritance/override, product and variant update, variant delete plus last-variant refusal, master rename/delete, cross-org rejection).
**Design note worth flagging:** HSN codes are *suggested from a fixed table of real codes, never generated*. Unlike SKUs and barcodes, an HSN determines the GST rate on a legal invoice — so the suggester returns null rather than guessing, and every suggestion stays editable. See `docs/03-database-design.md` §22.

## Phase 13 — UI refresh, breadcrumbs, barcode labels & log hygiene (post-launch enhancement) — ✅ Complete
Feedback from running the app: the interface looked dated and static, there was no way back up a navigation trail, printed barcode labels didn't exist despite barcodes being generated since Phase 11, and the dev terminal logged every request's full header block.
**Exit criteria:** the app reads as a current product and feels responsive under interaction; every page shows a navigation trail; a shopkeeper can print scannable labels for one product or a multi-selected batch; the API log is readable at a glance.
**Delivered:** a re-themed design system (indigo/violet, layered surfaces, larger radii, layered shadows, eased transitions, press feedback, slim scrollbars, refreshed Button/Card/Input primitives and shell) achieved by swapping token *values* while keeping token *names*, so all 36 screens re-skinned untouched; a pathname-derived `Breadcrumbs` component in the shell; in-repo EAN-13 SVG rendering (`lib/ean13.ts`, `components/ui/barcode.tsx`) plus a `/products/barcodes` roll-label print page with size presets and copies-per-label, wired to per-row and multi-select bulk actions on the Products list and to the product detail page; and pino-http reconfigured to log one readable line per request with health checks silenced. Covered by `apps/web/lib/ean13.test.ts`.
**Not delivered:** a dark-mode toggle (light-only for now), and A4 sheet-grid label layout — the label page targets roll/thermal printers, which is what was asked for; adding a sheet layout later is a second template on the same page, not a rework.

## Phase 16 — Production security hardening — ✅ Complete (with one documented gap)
Pre-deployment pass over everything that only matters once the app is public.
**Exit criteria:** the service refuses to start misconfigured; abuse is rate-limited; transport and cookies are correct behind a load balancer; and every remaining gap is written down rather than discovered later.
**Delivered:** boot-time production guardrails (placeholder/low-entropy `JWT_SECRET`, non-TLS `DATABASE_URL` and non-HTTPS `WEB_ORIGIN` all refuse to start); `trust proxy` as an explicit hop count, without which per-IP rate limiting and audit-log IPs are both wrong behind a proxy; a global per-IP rate limit layered under the existing auth limits; HTTPS enforcement, HSTS, a locked-down API CSP, `no-store`, anti-framing/sniffing headers; a CORS allow-list that never reflects an arbitrary origin; configurable cookie `SameSite` for cross-site deployments; a length-first password policy with a common-password denylist; `npm audit --audit-level=high` gating CI; and `docs/07-production-security.md` as the deployment runbook. Covered by `apps/api/test/security.test.ts`.
**Documented gap:** tenant isolation remains application-layer. `apps/api/security/rls-policies.sql` holds ready Row-Level Security policies but is deliberately **not** applied — enabling it without the accompanying `withOrgContext()` refactor makes every query return zero rows, which in production is indistinguishable from data loss. Rollout steps, required code change and rollback are in that file and in §4 of the security doc.

## Phase 17 — Scale & capacity hardening — ✅ Complete
Triggered by a direct question — "how many clients can this handle?" — and answered by auditing the code rather than guessing.
**Exit criteria:** the known load multipliers are removed, limits hold across replicas, the hot search path is indexed, and capacity can be measured rather than estimated.
**Delivered:** the notification poller's N+1 replaced with one query per reference table plus a batched insert and a 2-minute per-org scan throttle (it previously scaled with users × low-stock items and ran on every poll); connection pool sizing via `DB_POOL_MAX` with `statement_timeout` and `idle_in_transaction_session_timeout` so no single query can drain the pool; Redis-backed auth rate limiting (shared counters across instances) with a circuit-breaking in-memory fallback so a Redis outage degrades limits instead of taking tills offline; migration 0013 adding trigram indexes on SKU/barcode/phone and an access-pattern-matched sales index; and a dependency-free load-test harness (`npm run loadtest`) reporting p50/p95/p99 per endpoint. Written up in `docs/08-scaling.md`.
**Explicitly not addressed, and documented as ceilings:** unbounded `stock_ledger`/`audit_logs` growth (needs monthly partitioning), live report aggregation (needs materialised rollups), no caching layer despite Redis being connected, single primary with no read replicas, and no per-tenant quotas.

## Sequencing Rationale (why this order and not another)
- **Tenancy before everything** — retrofitting multi-tenant isolation onto tables built without it is the single most expensive mistake to fix later; it goes first even though it's invisible to a demo.
- **Catalog/Inventory before POS** — POS is a *consumer* of stock truth, not the owner of it; building POS first would require throwaway mocks that get discarded, wasting the exact incremental-approval cycles you asked to preserve.
- **Reports after Sales, not before** — every report in 04-module-breakdown.md aggregates over sales/purchase/inventory tables that don't exist yet in earlier phases; building report screens first would mean building them twice.
- **Hardening last, not "whenever"** — treating security/performance as a final gate (rather than "eventually") is deliberate: it's the difference between a prototype and the "production-ready, sellable SaaS" goal stated in your brief.
